Actually using the Polars lazy API

scan, collect, and the optimiser doing work you didn’t ask for

Python
Polars
Why scan_parquet beats read_parquet, what the query optimiser does before your query runs, and what out-of-core spilling changed in 1.42.
Published

August 26, 2026

I’ve been using Polars for a while now and, for an embarrassingly long stretch of that, I used it exactly like pandas. pl.read_csv, chain some operations, look at the result. It worked, it was faster than what I’d been doing, and I stopped there.

Which meant I was skipping the part that makes Polars different.

Eager and lazy

Every Polars reader has two forms. pl.read_parquet returns a DataFrame. pl.scan_parquet returns a LazyFrame.

import polars as pl

eager = pl.read_parquet("participants.parquet")
lazy = pl.scan_parquet("participants.parquet")

The eager version reads the file. The lazy version reads the schema and makes a note. Nothing else happens until you call .collect().

That sounds like a small difference and it isn’t. When you build a query lazily, Polars sees the whole thing before it runs any of it, and gets to rewrite it:

q = (
    pl.scan_parquet("participants.parquet")
    .filter(pl.col("program") == "entrepreneurship")
    .filter(pl.col("cohort_year") >= 2024)
    .select("participant_id", "program", "cohort_year", "completed")
)

df = q.collect()

Written eagerly, that reads every column of every row, then throws most of it away twice. Written lazily, Polars pushes both filters and the column selection down into the scan, so the reader skips row groups that can’t match and never touches the columns you didn’t ask for.

An existing DataFrame can join the party with .lazy(), though by then you’ve already paid to read the file:

q = pl.DataFrame({"foo": ["a", "b", "c"], "bar": [0, 1, 2]}).lazy()

What the optimiser actually does

The rewrites have names, and it’s worth knowing them because they explain why some query shapes are much faster than others. From the optimisations page in the user guide:

Predicate pushdown applies filters at the scan, as early as possible. Projection pushdown reads only the columns the query needs. Slice pushdown loads only the slice you asked for, so .head(10) after a join doesn’t materialise the whole join. Common subplan elimination caches subtrees and file scans used by more than one branch of the plan. There are others: simplifying expressions, coercing types to the smallest thing that works, estimating cardinality to choose a group by strategy, and reordering joins to keep memory pressure down.

You don’t invoke any of these. You get them by using scan_* and collect() instead of doing it yourself.

Reading the plan

.explain() prints what Polars intends to do. It takes a bit of squinting, but the useful habit is comparing the optimised plan against the unoptimised one:

print(q.explain(optimized=False))
print(q.explain())

The thing to look for is where your filters ended up. If a predicate appears down at the scan node, pushdown worked. If it’s still sitting up near the top of the plan, something blocked it, and the usual culprit is a Python function the optimiser can’t see through. A map_elements call in the middle of a chain is opaque: Polars can’t reason about it, so it stops rewriting at that point.

That’s a decent argument for expressing things as native expressions where you can, or wrapping your own logic in a custom expression namespace so it stays an expression the optimiser can still work with.

Schema errors before the data

This is the benefit I didn’t expect to care about and now rely on constantly.

A LazyFrame knows its schema without reading the data, and Polars type-checks the whole query at collect time. So a typo in a column name fails immediately, rather than twenty minutes into a job:

q = (
    pl.scan_parquet("participants.parquet")
    .select("participant_id", "cohort_yr")  # typo
)

q.collect()  # raises before any data is read

If you want the schema itself, use collect_schema() rather than the .schema property. On a LazyFrame it makes the resolution explicit, which matters because resolving a schema can require work.

print(q.collect_schema())

For the kind of work I do, where a script runs against a folder of files that were exported by someone else last quarter, failing at second zero instead of minute twenty is worth more than any speed-up.

Larger than memory

collect() brings the result into memory. If the result doesn’t fit, that’s a problem, and the lazy API is also the answer here.

The streaming engine processes the query in chunks rather than materialising everything:

df = q.collect(engine="streaming")

Better still, if the output is going straight back to disk, skip the in-memory step entirely and use a sink:

(
    pl.scan_parquet("raw/*.parquet")
    .filter(pl.col("cohort_year") >= 2024)
    .sink_parquet("clean/participants.parquet")
)

sink_parquet streams from source to destination. The full result never has to exist in memory at once, which turns “this crashes my laptop” into “this takes a few minutes”.

Polars 1.42, released in June 2026, added naive out-of-core spilling. When a query needs more memory than it has, it can now spill to disk rather than falling over. Naive is the maintainers’ word, not mine, and it’s a safety net rather than a strategy: a query that spills is slower than one that doesn’t. Still, the failure mode changed from a crash to a slowdown, and that’s the failure mode I’d rather have at 5pm.

The same release added an experimental strict mode and support for SQL’s implicit JOIN syntax, if either of those is your sort of thing.

The habit worth forming

The rule I’ve settled on is boring: start every query with scan_, end it with collect() or a sink_, and put everything else in between.

It costs nothing when the data is small, because the optimiser has less to do and does it quickly. It costs nothing to read, because the middle of the chain looks identical either way. And on the day a file turns out to be much bigger than you expected, you’ve already written the version that copes.

Worth knowing: Polars 2.0 is in release candidate, and there’s an upgrade guide already. I haven’t moved yet, but I’d rather find out what changes before it lands than after.
