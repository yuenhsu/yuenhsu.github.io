How this Quarto site is actually put together

Two years of small decisions, documented before I forget them

Quarto
A tour of the _quarto.yml, the two listing pages, shared metadata, and the drafts folder that keeps half-finished posts out of the build.
Published

August 26, 2026

I wrote about moving from WordPress to Quarto a couple of years ago, and that post covered getting a private repo onto cPanel and pointing a domain at the rendered output. What it didn’t cover is the part I actually spend time on, which is how the site itself is arranged.

This is that write-up. Partly for anyone setting up something similar, mostly so future me stops re-deriving decisions I already made.

The shape of the project

The whole site is a Quarto website project. Nothing exotic:

Project structure
_quarto.yml          # site config
index.qmd            # home, about block + recent posts
about.qmd
projects.qmd
posts.qmd            # full post listing
posts/               # published posts
  _metadata.yml
  images/
drafts/              # half-written posts
  _metadata.yml
assets/              # theme, fonts, images, analytics
references.bib
requirements.in

Quarto’s blog template puts each post in its own subdirectory with an index.qmd inside. I use flat .qmd files in posts/ with a shared images/ folder instead. That’s a trade-off I’d probably reverse if I started over. Per-post directories keep each post’s images next to the post, so deleting a post deletes its assets. My flat images/ folder is now a pile of files with names like power_bi_setup_min_card.png and no obvious owner.

Two listings, different jobs

The site has two listing pages, and they’re configured differently on purpose.

posts.qmd is the archive. Everything, newest first, with descriptions and categories so the sidebar filter works:

posts.qmd
---
title: "Posts"
subtitle: "Sharing my solution to very specific issues/questions and other fun things"
comments: false
title-block-banner: true
listing:
  contents: posts
  date-format: "YYYY/MM/DD"
  sort: "date desc"
  type: default
  categories: true
  fields: [date, title, description, categories]
---

categories: true is what generates the clickable category sidebar. It reads from the categories field in each post’s front matter, which means it only works if you actually set it. I did not, for the first several posts, so my category sidebar is thinner than it should be. Something to fix.

index.qmd is the shop window. Same contents: posts, but capped at five, in table layout, with the filter and sort controls turned off:

index.qmd
listing:
  id: post-listing
  contents: posts
  sort: "date desc"
  type: table
  max-items: 5
  fields: [title, description]
  sort-ui: false
  filter-ui: false

The id matters. Giving the listing an id lets you place it anywhere in the document body with a matching empty div, rather than having Quarto drop it wherever it likes:

index.qmd
## Recent Posts

::: {#post-listing}
:::

The same trick puts the about block above it, with about: id: hello-block in the front matter and a ::: {#hello-block} div in the body. Two listings and an about block on one page, each exactly where I want it.

Shared metadata beats repeating yourself

Quarto reads _metadata.yml from a directory and applies it to every document inside. Mine is short:

posts/_metadata.yml
format:
  html:
    author: "Yu-En Hsu"
    toc: true

Author and table of contents, set once. Every post inherits both, and no post front matter has to mention either. The Quarto blog template also puts freeze: true here by default, which caches computational output so old posts don’t re-run their code on every site render. I haven’t turned it on, because most of my posts set execute: eval: false and don’t run anything at build time anyway. If I write more posts that hit live APIs, freeze goes in this file first.

The drafts folder

This is the bit I’d recommend to anyone.

drafts/_metadata.yml
draft: true

One line, applied to a whole directory. Anything in drafts/ is a draft, permanently, without me remembering to add draft: true to individual files.

Drafts show up when you run quarto preview so you can work on them, but render blank and stay out of listings, navigation, the site map, and site search when you render the site properly. See Website Drafts for the full behaviour.

The related setting lives in _quarto.yml:

_quarto.yml
website:
  draft-mode: visible

draft-mode controls what happens to draft content in the rendered site. Publishing a draft is then a two-step move: fix the writing, then move the file from drafts/ to posts/. No front matter edit required, because the draft: true came from the folder, not the file.

Theme, and the part where I lose an afternoon

_quarto.yml
format:
  html:
    theme:
      - cosmo
      - assets/theme1.scss
    toc: true
    highlight-style: "github-dark"
    link-external-newwindow: true
    link-external-filter: "(yuenhsu|yhsu10)"
    link-external-icon: true

theme takes a list. First entry is a Bootswatch theme, the rest are SCSS files layered on top. So cosmo does the heavy lifting and theme1.scss holds my overrides, which means I never fork a whole theme to change a font.

highlight-style: "github-dark" is there because I went and screenshotted every single one of them rather than picking one like a normal person.

The two link-external-* options are worth knowing about. Quarto adds an icon to external links and opens them in a new window, and link-external-filter is a regex for what counts as internal. Mine lists both my domains, so links between my own pages don’t get the external treatment. Without it, every internal link picks up a little arrow icon and steals a browser tab.

Comments and citations

Comments are giscus, which stores threads as GitHub Discussions on the site’s own repo:

_quarto.yml
comments:
  giscus:
    repo: yuenhsu/yuenhsu.github.io
    mapping: pathname
    theme: preferred_color_scheme
    reactions-enabled: true
    loading: lazy

mapping: pathname ties a discussion thread to the page’s path, so the thread follows the URL. Rename a post file and you orphan its comments, which is a good reason to get filenames right the first time. theme: preferred_color_scheme makes the comment box follow the reader’s dark mode instead of sitting there glowing white.

Setting comments at the top level turns them on everywhere, so pages that shouldn’t have them opt out individually with comments: false. posts.qmd and index.qmd both do.

Citations come from a single references.bib declared once at project level. Any post can then use [@citekey] without its own bibliography declaration, which is how the US states post cites the CIA World Factbook and the altair post cites hrbrthemes.

Reproducing the environment

requirements.in lists the Python packages the posts need, compiled to a pinned requirements.txt. It’s short, and it’s essentially a list of everything I’ve written about:

requirements.in
altair
polars[pandas,excel]
PyYAML
jupyter
python-dotenv
jupyter-cache
selenium
great_tables
geopandas[all]

Keeping .in and .txt separate means the .in file says what I want and the .txt says exactly what got installed. When a render breaks on a new machine, the pinned file is the thing that tells me what changed.

What I’d do differently

Three things, in order of how much they’d have saved me:

Per-post directories, as above. Assets belong with their post.

Categories from day one. They cost nothing to add while writing and are tedious to backfill, which is why I still haven’t.

A CSS variables layer in theme1.scss instead of scattered overrides. Every time I want to change the accent colour I go hunting.

None of these are urgent. All of them are the kind of thing that’s free at the start and annoying later, which is most of what I’ve learned about running a site.
